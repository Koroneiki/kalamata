# AGENTS.md

## Project

Kalamata is a private Electrobun desktop application. Its Vue frontend runs in the main webview, the Electrobun Bun process starts at `src/bun/index.ts`, and the Steam depot downloader lives in `src/backend`.

## Core stack

- Vue 3 with Composition API and `<script setup>`
- TypeScript
- Tailwind CSS v4 with semantic design tokens in `src/assets/index.css`
- Pinia for client-side application state
- Pinia Colada for asynchronous data fetching and query caching
- Vue Router with hash history for packaged Electrobun URLs
- shadcn-vue for generated UI primitives

## Architecture

```text
src/
├── api/             # API and Electrobun RPC calls, one file per entity
├── assets/          # Static assets and global styles
├── backend/         # Bun-based Steam depot downloader
├── bun/             # Electrobun process entrypoint and RPC host
├── components/
│   ├── ui/          # Generated shadcn-vue components (DO NOT MODIFY)
│   ├── forms/       # Entity-specific form components
│   ├── tables/      # Entity-specific table components
│   └── shared/      # Reusable custom components
├── composables/     # Vue composables
├── layouts/         # Layout components
├── lib/             # Third-party adapters and shared libraries
├── mainview/        # Electrobun webview HTML and Vue entrypoint
├── router/          # Vue Router configuration and guards
├── stores/          # Pinia stores
├── types/           # Shared frontend TypeScript types
├── utils/           # Focused utility functions
└── views/           # Route-level page components
```

Keep frontend code out of `src/backend` and `src/bun`. The frontend reaches native functionality through typed Electrobun RPC wrappers in `src/api`; it must not import backend modules or manage `steam-user` directly.

Use Pinia for durable client state. Use Pinia Colada for remote or RPC-backed asynchronous state, caching, invalidation, and mutations. Do not copy query results into Pinia stores unless a consumer needs state that must outlive or diverge from the query cache.

When code changes include non-obvious behavior, assumptions, or constraints, add a short comment explaining why the code is necessary.

## UI components

Files under `src/components/ui` are generated by shadcn-vue. **DO NOT MODIFY THEM MANUALLY.** Install or update primitives through the CLI:

```sh
bunx --bun shadcn-vue@latest add <component-name>
```

Build application-specific behavior in custom components under `forms`, `tables`, or `shared`, wrapping `ui` primitives as needed. Use the `cn` helper from `@/lib/utils` for conditional Tailwind classes and use semantic design tokens instead of hard-coded theme colors.

shadcn-vue components are based on reka-ui v2 and use `modelValue` / `update:modelValue` rather than HTML-native state props:

- Bind `Switch` with `v-model` or `:model-value` plus `@update:model-value`; do not use `checked`.
- Bind `Select` with `v-model` or `:model-value` plus `@update:model-value`; do not use `value` or `selected`.

```vue
<Switch v-model="myBool" />

<Switch
  :model-value="item.is_active"
  @update:model-value="handleToggle(item)"
/>
```

## Playwright and Electrobun

A normal browser lacks Electrobun's injected RPC bridge. For browser UI tests:

- Use `page.addInitScript` before hash-route navigation to mock `window.__electrobun` and `window.__electrobunBunBridge.postMessage`.
- Return RPC responses through `window.__electrobun.receiveMessageFromBun`; derive methods and payloads from `src/types/rpc.ts` and `src/api`.
- Emit Bun messages with `{ type: 'message', id: 'downloadQueueChanged', payload }` containing the full queue snapshot.
- Startup needs `getLibrary` and `getDownloadQueue`. App routes also need their summary and details requests.
- Keep the mock inside Playwright. Do not add RPC bypasses to production code.
- Clear `sidebar_state` when screenshots require an expanded sidebar, and stop any Vite server started for the test.
- Playwright covers UI state only. Verify native dialogs, filesystem behavior, Steam access, downloads, and real RPC separately.

## Common tasks

Add a shadcn-vue button:

```sh
bunx --bun shadcn-vue@latest add button
```

Add a route in `src/router/index.ts`. Route-level views must be lazy loaded:

```ts
{
  path: '/example',
  component: () => import('@/views/ExampleView.vue'),
}
```

Put route guards in `src/router`. Keep API or Electrobun RPC calls in `src/api`, composable orchestration in `src/composables`, and route components in `src/views`.

## Database migrations

- Define schema changes in `src/db/schema.ts`, then run `bunx drizzle-kit generate`.
- Commit the SQL, journal, and snapshot together. Never edit an applied migration; generate another one.
- Review all generated SQL before applying it.
- Review SQLite table rebuilds for correct constraints and data-copy order.
- Verify fresh database creation and, for data or constraint changes, upgrades from a populated database.

## Fallow code quality

- Run `bun run fallow` after non-trivial changes. Use `bunx fallow dead-code`, `bunx fallow dupes`, or `bunx fallow health` when investigating one category.
- Remove real dead code and duplication, but check runtime entry points, generated code, dynamic imports, and package side effects first.
- Treat complexity as a review prompt. Refactor risky control flow, not cohesive workflows or Vue templates, and do not add metric-only wrappers.
- Add focused tests for risky behavior and check changed UI at desktop and narrow widths.
- Keep ignores narrow and explained. The existing health report may exit nonzero; reject new or worse findings in modified paths.
